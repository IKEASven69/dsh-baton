# 搜索联动设计 — 收件箱过滤 → 跨会话搜索的分级路线

> 需求来源：aisle 的核心卖点（"full-text search a word that only appears in a reply"）；本机八家会话存量约 250+（zcode 98 + opencode 109 + pi 25 + workbuddy 14 + claude 1）；DSH 生态已有 AI Vault 规划（orca UPGRADE-LIST U-2：全 CLI 会话扫描/搜索/恢复）。

## 需求分级（按真实频率）

| 级别 | 场景 | 现状 |
|------|------|------|
| L1 | 收件箱内找某张卡（pending ≤50） | ✅ 0.3.0 已做（过滤框：标题/来源/编号） |
| L2 | 跨八家**历史会话**找"哪次聊过 X" | ❌ 未做——这正是 AI Vault 的范围 |
| L3 | 历史会话**全文**搜索（一个只出现在回复里的词） | ❌ aisle 的卖点；成本高（索引/分词），需求频率存疑 |

## 路线决策

**不自建索引，联动 AI Vault。**

- orca UPGRADE-LIST U-2 已规划 AI Vault（全 CLI 会话扫描/搜索/恢复）——跨家扫描、索引、检索是它的职责；dsh-takeover 自建就是重造轮子 + 双份维护税（opencode 存储迁移这种上游变动已经证明适配器是持续负债）
- 联动方式（AI Vault 落地后）：`/resume-*` 的候选列表与设置卡消费其检索 API；dsh-takeover 零改动或仅加一个"搜索由 AI Vault 提供"的入口标注
- 时序：AI Vault 未落地前，L2/L3 保持不做（pending 过滤已覆盖高频场景）；落地后本插件按其 API 对接，预计半天

## 明确不做

- dsh-takeover 内建全文索引/分词（职责越界）
- L3 全文搜索的自研（等 AI Vault 的口径，避免二次返工）
