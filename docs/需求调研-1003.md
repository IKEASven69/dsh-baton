## 二、升级方向（建议排期）

**P1（小成本高确定，先做）**
1. **假 0 哨兵**：适配器存储根存在但为空 → `note` 提示"布局可能已迁移/为空"，设置卡矩阵行显黄字，不再静默 0（casr #26 + 本机 opencode 实锤，双案底）
2. **空 cwd 警告**：会话 directory 为空 → 六段卡「停在哪」自动追加"⚠ 无工作区信息，接手前先确认目录"（casr #20 同类）

**P2（一次 agent 会话可交付）**
3. **收件箱新卡通知**（10-03 已落地）：push/取件后宿主通知。调研结论：可实现，最接近形态 = `ctx.userQuestions.ask` 阻塞式问答面板（toast/系统通知无插件挂点）；服务缺席、客户端离线（NO_PROVIDER）、subagent 持有 agent（DELEGATED_CALLER）一律静默降级为工具结果文本
4. **新 provider**：Kiro CLI 适配器（readers 模板成熟，sqlite/文件二选一）；Grok Build 官方 CLI 核对 updates.jsonl 兼容性
5. **设置卡自动刷新**：pending 变化轮询/事件刷新（aisle #40 同款）

**P3（文档/叙事层）**
6. **跨设备一句话**（已落地）：README「跨机器接力」小节：`HANDOFF_HOME` 指向同步盘或 git 仓库即多机接力
7. **README 竞品段**：直说 vs casr/aisle/agentctxsync 的机制差异（接管+审计语义 vs 转换/导航/同步）；「只读不写会话」免疫 casr #10 类转换事故
8. **handoff: 1 采用列表**：agent-handoff 仓 README 登记采用者（JarvanAI 撞名 + 协议叙事撞车，占位要快）

## 功能候选（决策版）

| 候选功能 | 证据来源 | 成本 | 判定 |
|----------|----------|------|------|
| **交接卡双形态输出**：给人的 Playbook/ADR（markdown）+ 给机器的接手信封（JSON <1200 chars，token 受限接手场景） | JarvanAI 核心卖点（Human Playbook + Machine Envelope 双输出） | 中 | P3 观望：等真实需求出现再做 |
| **蒸馏指令层加 final-state anchoring 规则**：从最终共识回填理由，主动剔除"已被推翻的中间结论"，而非仅标 MISMATCH | JarvanAI 的 Reverse Verdict Anchoring + FSM 剪枝；我们四态账本只做标注不做剪枝 | **零代码**（skills/resume.ts 指令层加一条规则） | P1 采纳：模型侧一句规则，蒸馏质量直接受益 |
| **四态覆盖率统计**：done 段每条陈述的账本状态标注率（多少条没标状态）——审计语义产品化 | 自查：四态靠模型自觉，无覆盖率度量 | 低 | P2 备选 |
| **HTML 单文件导出**（卡片/收件箱报告） | Claude Code 官方仓多个 /export(html) 请求；我们已有零依赖 Blob 下载模式 | 低 | P2 备选 |
| **MCP server 形态**：非 DSH 的 agent 经 MCP 读收件箱/拉会话——分发面从 DSH 扩到全生态 | agentctxsync 带 MCP server；我们只有 DSH 插件面 | 中 | 观望：等 DSH 内口碑先立住 |
| **跨会话搜索 / AI Vault 联动** | aisle 卖点；orca U-2 规划 | — | 已有设计文档（搜索联动设计.md），等 AI Vault 落地 |
| 会话分享链接（share_url） | opencode session_share 表原生支持 | — | 不做：依赖各家原生分享，非交接场景 |
